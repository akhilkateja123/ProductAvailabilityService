Product Availability Service

A backend microservice case study — architecture, implementation, and the path to production.

01 — Problem

The ask

Build a lightweight Product Availability microservice: one REST endpoint that returns real-time stock status for a product SKU, for internal consumers like checkout and storefront.

Contract

  • GET /availability/{productId}
  • JSON response
  • 200 / 400 / 404 / 500

Business rule

  • inStock = true when quantity > 0
  • inStock = false when quantity = 0
  • Missing product → 404

Stack

  • Java 21 + Spring Boot 3
  • Maven
  • In-memory data (10 SKUs)

01 — Problem

First question: what is a "productId"?

Aritzia's storefront runs on Salesforce B2C Commerce (confirmed by the case study, and by the PWA Kit bundle paths visible on aritzia.com). SFCC uses a master/variant product model.

Master product
(the style)
→
Black / S
Black / M
Cream / S
Cream / M

Each variant is its own SKU — its own inventory record, own availability.

Answering the actual question: colors are not the same SKU, and sizes are not the same SKU — every color × size combination is its own variant SKU with its own quantity. The master style only carries shared content (title, images, price). So productId in this exercise = a variant-level SKU, matching SFCC's own model — not the style ID shown in a PDP URL.

Validation: drawing the 400 / 404 line

productId is rejected with 400 unless, after trimming, it matches ^[0-9]{1,20}$

Any caller input echoed into an error or log line is capped at 50 characters with control characters replaced, so oversized input can't bloat logs and embedded newlines can't forge log entries.

02 — Architecture

Layered design

Controller

@RestController — thin. No validation logic lives here; it delegates immediately.

Service

Validates productId first (fail fast, before any I/O), then checks cache, then repository.

Validator

Single source of truth for the productId format rule — used nowhere else.

Repository

Interface + in-memory implementation — swappable for a real datastore without touching callers.

API gateway / edge

04 — Quality

Tests & error handling

47 automated tests

Validation & model (18) — leading zeros preserved, internal whitespace rejected, max-length boundary, null handling, negative quantity rejected

Service & caching (6) — in-stock, out-of-stock, not-found, invalid ID never touches the repository; three requests for one SKU hit the repository once

HTTP integration (10) — full round-trip for every status code: 200, 400, 404, 405, and a 500 with the data source mocked to fail

Filters & logging (13) — 429 after the burst, limits tracked per client, request-ID propagation, JSON log format, input sanitizing

Centralized error handling

One @RestControllerAdvice maps exceptions to responses — controllers never build error JSON, and every error shares one body shape.

400 Malformed or missing productId

404 No such SKU, or no such route

405 Framework errors keep their real status

429 Rate limit (written by the filter, same body)

500 Only genuinely unexpected failures, logged at ERROR

04 — Quality

Logging, caching, rate limiting, docs

  • Request tracing — every request gets an X-Request-Id (the caller's own, if safe, otherwise generated), attached to every log line for that request and returned as a response header. One summary line per request: method, path, status, latency.
  • Cloud-native logs — in the container, logs are one JSON object per line with severity, message, time and requestId, which Cloud Logging parses natively; locally they stay readable plain text.
  • Caching — Caffeine, 8s TTL, in-process, keyed on the validated ID so " 10001" and "10001" share one entry. Confirmed live: repeat requests drop from ~70ms to ~40ms.
  • Rate limiting — token bucket per client IP (20 req/sec), servlet filter ahead of the controller. Demo-grade by design: the IP comes from a header the caller can set, so production limits belong at the gateway, keyed by API key.
  • OpenAPI / Swagger — auto-generated from the annotated controller, live on the deployed service.
  • Container — multi-stage build, JRE-only runtime image, runs as an unprivileged user.
{"time":"2026-09-30T23:32:00.969Z","severity":"WARNING","message":"Invalid productId rejected: productId must be 1-20 numeric digits with no spaces; got: 'abc'","requestId":"demo-123"} {"time":"2026-09-30T23:32:00.973Z","severity":"INFO","message":"GET /availability/abc -> 400 in 10ms","requestId":"demo-123"}

04 — Quality

CORS: why the endpoint allows any origin

The service allows cross-origin GET requests to /availability/** from any origin. Here's why, and what changes in production.

Why it's needed

Browsers won't let a page read a response from a different origin unless the server opts in. The live demo console runs on a different origin than Cloud Run, so without this its calls would reach the service but the browser would withhold the response. curl, Postman and service-to-service calls don't enforce CORS at all.

Why allow-all is fine here

The endpoint is read-only, unauthenticated, uses no cookies or credentials, and returns non-sensitive demo data. CORS isn't access control; it only decides which web pages may read responses in a browser, and anyone can already call the endpoint directly. Scope is narrow: only this path, only GET.

Production

Real callers (checkout, storefront) are internal services, so the service would sit behind Cloud Run IAM or service-to-service auth via a gateway, not be publicly reachable. If a browser client needed direct access, allowed origins would be the specific storefront domains, not *.

05 — Path to production

Target architecture: multi-instance, shared cache

05 — Path to production

Why one instance isn't enough

With multiple Cloud Run instances, each holds its own independent in-process cache. Two customers hitting the same SKU at the same moment can get different answers.

Today (demo)

  • In-process cache (Caffeine)
  • 1 instance — no consistency question
  • Zero extra infra, zero network hop

Production

  • Memorystore (managed Redis) shared across all instances
  • Reached over a Serverless VPC Connector
  • Every instance sees the same cached value

06 — Wrap-up

What I'd do next

  • Wire up a shared cache (Memorystore) the moment a second instance exists
  • Replace the in-memory data source with real inventory (OMS / SFCC), event-driven
  • Add SLOs and alerting on top of the structured logs, before this sees real traffic
  • Move rate limiting to the gateway, keyed by API key instead of a caller-supplied IP header, and tune thresholds against real flash-sale traffic
  • Put checkout on a cache-bypassing read, with stock reserved at the OMS; the 8-second cache stays for storefront and product pages
  • Lock down access: Cloud Run IAM or service-to-service auth, and CORS limited to real storefront origins

Appendix

Alternatives considered

Compute: Cloud Run (chosen) vs. GKE

Cloud Run: fully managed, scales to zero, minimal setup — right fit for one small stateless service.

GKE: full cluster control, justified once running many services with shared infra needs; no scale-to-zero, meaningfully more to operate.

Cache: Memorystore (prod) vs. in-process (demo)

Memorystore: managed Redis, sub-ms latency, needs a VPC connector. Solves the multi-instance consistency problem.

In-process: zero infra, but each instance holds an independent, inconsistent copy once scaled out.

Edge / API gateway

Cloud Run + Cloud Armor (chosen) — managed HTTPS + WAF/edge rate limiting, minimal setup. Google API Gateway — lighter managed layer, API-key auth, request validation. Apigee — full API management (developer portal, quotas, analytics) — justified with many external consumers, heavier than this scope needs.

Appendix

Race conditions

This exercise is read-only, so there's no write path to race on. In production: two shoppers add the last unit to cart at the same instant.

Customer A
Read qty = 1
Check qty > 0 ✓
Add to cart
Decrement qty
Customer B
Read qty = 1
Check qty > 0 ✓
Add to cart
Decrement qty

Both read qty=1, both pass the check, both decrement — final qty = -1. Oversold.

Optimistic locking

UPDATE stock SET qty=qty-1, version=version+1 WHERE id=? AND version=? AND qty > 0

Retry on conflict. Simple, no extra infra — good for low-contention SKUs.

Reservation + TTL

Reserve 1 unit for 10 minutes at add-to-cart; release automatically if checkout doesn't complete. Standard e-commerce pattern.

Atomic decrement

Push check-and-decrement into one atomic op (e.g. Redis DECR with a floor check). Removes the race by construction — best for flash-sale SKUs.

Multi-region

Cloud Run deploys to one region at a time — multi-region is composed, not a single setting.

Global HTTPS
load balancer
⇉
us-west1
Cloud Run + Memorystore
europe-west1
Cloud Run + Memorystore
asia-northeast1
Cloud Run + Memorystore

Serverless NEG per region — latency-based routing via Google's anycast network.

The catch: Memorystore is regional too. Each region needs its own cache. The thing that actually has to be globally consistent is the inventory source of truth — typically a globally-replicated database (e.g. Cloud Spanner) or accepted eventual consistency between regions.
